## 1. Технологический стек

| Слой | Технология | Версия |
|---|---|---|
| Платформа | Expo (managed workflow) | **SDK 54** |
| Язык | TypeScript (strict) | ~6.0 |
| UI-фреймворк | React Native | 0.81.5 |
| React | React | 19.1.0 |
| Состояние | Zustand (+ persist в AsyncStorage) | ^5 |
| БД | expo-sqlite (новый async API) | ~16.0.10 |
| Секреты (PIN/пароль) | expo-secure-store | ~15.0.8 |
| Навигация | @react-navigation (native-stack + bottom-tabs + drawer) | v7 |
| Графики | react-native-gifted-charts | ^1.4.77 |
| Тесты | Jest + jest-expo + @testing-library/react-native | — |

> **Важно про версию SDK**: проект специально закреплён на SDK 54, а не на самой новой (57), потому что мобильные магазины приложений на момент разработки ещё не выкатили Expo Go с поддержкой SDK 57. Если в будущем менять версию Expo — сначала проверить, какую версию поддерживает Expo Go на реальном устройстве (Profile → SDK version в приложении), и поднимать SDK только вслед за этим.

Полный список зависимостей и точных версий — в `package.json`.

### Отклонения от исходного ТЗ (сознательные, с причиной)
- **`victory-native` → `react-native-gifted-charts`**: victory-native требует `@shopify/react-native-skia`, который не работает в обычном Expo Go (нужен custom dev client). gifted-charts даёт тот же набор графиков (пироги, столбцы, линии) на чистом `react-native-svg`.
- **`expo-av` → `expo-audio`**: `expo-av` официально удалён из Expo SDK, начиная с 55-й версии.
- **`expo-speech-recognition`**: не подключён как реальный пакет (требует custom dev client, несовместим с Expo Go) — экран голосового ввода оставлен как контролируемая UI-заглушка.

## 2. Дизайн-система

- Основной цвет: `#1E3A5F` (тёмно-синий) — заголовки, навбар, статус-бар.
- Акцент: `#7F1D1D` (бордовый) — кнопки, иконки расходов, прогресс-бары лимитов.
- Вторичный синий: `#2563EB` — карточки, иконки доходов, диаграммы.
- Фон: `#F8FAFC`, карточки — белые с тенью.
- Дополнительные цветовые схемы на выбор в Настройках: синяя (по умолчанию), бордовая, зелёная, фиолетовая — с анимированным переходом.
- Отдельно переключается светлая/тёмная тема (не привязана к цветовой схеме).
- Файлы: `src/theme/colors.ts`, `src/theme/index.ts`, `src/theme/ThemeContext.tsx`.
- **Форматирование чисел**: `formatCurrency`/`formatNumber` (`src/utils/format.ts`) собирают строку вручную (пробел как разделитель тысяч, запятая как десятичный разделитель, например «350 000,25»), не полагаясь на `Intl.NumberFormat('ru-RU')` — Hermes в Expo Go не всегда несёт полные ICU-данные локали, из-за чего Intl мог на реальном устройстве тихо откатиться к «350000.25». Используется для всех сумм и процентных ставок (кредиты, вклады, кэшбэк) — там, где раньше проценты/суммы выводились напрямую через `{value}%`, теперь тоже проходят через `formatNumber`.

## 3. Архитектура и структура проекта

```
/src
  /components   — переиспользуемые UI-компоненты (Card, AppButton, ProgressBar, ...)
  /screens      — экраны, сгруппированы по разделам (auth, onboarding, dashboard, ...)
  /store        — Zustand: settingsStore, authStore, financeStore
  /types        — общие TypeScript-интерфейсы (src/types/index.ts)
  /utils        — чистые функции: расчёты, форматирование, валидация, конвертация валют
  /hooks        — кастомные хуки (useFinancials, useBiometrics, useAppBootstrap, ...)
  /database     — SQLite: schema.ts, client.ts, repository.ts, seed.ts
  /navigation   — стек/таб/drawer навигаторы
  /__tests__    — Jest + RNTL тесты
```

### Данные
- Все финансовые сущности (транзакции, цели, кредиты, лимиты, вклады, инвестиции, долги, страховки, вишлист, уведомления, достижения, шаблоны, профиль) хранятся в **SQLite** (`src/database/schema.ts`), автосохранение при каждом изменении через `financeStore`.
- **PIN/пароль** хранится только в `expo-secure-store` — никогда не попадает в SQLite или обычный AsyncStorage.
- Настройки приложения (валюта, тема, звук/вибрация, факт прохождения онбординга) — в `settingsStore`, персистится через AsyncStorage.
- `authStore` хранит только метаданные входа (способ, счётчик неверных попыток, время блокировки) — тоже AsyncStorage, сам секрет — отдельно в secure-store.

### Навигация (файл `src/navigation/RootNavigator.tsx`)
Гейт на уровне корня, последовательно:
1. Экран настройки входа (если PIN/пароль ещё не заданы)
2. Экран блокировки/входа (если сессия не разблокирована)
3. Онбординг (если не пройден)
4. `MainDrawer` — основное приложение

`MainDrawer` (боковое меню) содержит:
- **Tabs** (нижние вкладки): Главная, Транзакции, Аналитика, Бюджет
- **Доходы**, **Расходы** — тот же экран `TransactionsScreen`, что и на вкладке «Транзакции», но открывается сразу с нужным типом (через `initialParams` в `createSimpleStack`, `src/navigation/SimpleStack.tsx`) — чтобы не искать переключатель внутри.
- Накопления, Кредиты и платежи, **Регулярные платежи**, Сравнение периодов, Хочу купить, Дополнительно, Профиль, Настройки
- Уведомления — доступны через колокольчик в шапке, скрыты из списка меню

**Кнопка «На главную» в шапке** (`HomeButton`, `src/components/HomeButton.tsx`, добавляется всем экранам через `createSimpleStack`): каждый экран бокового меню — корень своего отдельного стека, поэтому у него нет системной кнопки «назад»; единственным способом вернуться было открыть меню заново и найти «Главная» в списке (а у «Уведомлений» и того не было — при переходе туда через колокольчик кнопки открытия меню не было вовсе). Значок домика в правом верхнем углу — прямой переход на Главную одним нажатием с любого такого экрана, через глобальный `navigationRef` (`src/navigation/navigationRef.ts`), тем же способом, что уже использует колокольчик уведомлений.

> Пробовали переносить Накопления/Кредиты из бокового меню в нижние вкладки (для заметности), но по фидбэку от пользователя это было менее удобно — вернули на прежнее место в боковом меню. Доходы/Расходы, наоборот, по просьбе пользователя добавлены в боковое меню отдельными пунктами (раньше туда можно было попасть только через переключатель внутри «Транзакций»).

**Подсказки внутри разделов**: и «Накопления», и «Кредиты» показывают под своим переключателем (SegmentedControl) короткую поясняющую строку про текущую выбранную вкладку (`SEGMENT_HINTS` в соответствующих экранах) — чтобы было сразу понятно, что находится, например, в «Календаре» или «Счетах», не открывая их наугад.

## 4. Экран входа и безопасность

- Первый запуск: мастер настройки — выбор PIN (4 цифры) / Face ID / Touch ID / пароль, повтор для подтверждения, email для восстановления (заглушка, реального сброса по почте нет).
- Каждый следующий запуск: экран блокировки с PIN/биометрией/паролем.
- **3 неверные попытки → блокировка на 5 минут**, таймер переживает перезапуск приложения (хранится в persist-сторе).
- Кнопка «Забыли?» — сбрасывает вход и возвращает к мастеру настройки (демо-режим, реальной отправки email нет).
- Файлы: `src/screens/auth/AuthSetupScreen.tsx`, `AuthLockScreen.tsx`, `src/store/authStore.ts`.

## 6. Главный экран (Dashboard)

- Карточка **«Свободные средства»** = Доходы − Расходы (простой баланс по всем транзакциям, `calculateBalance`) — то, что реально осталось на руках. Кредитные платежи и отчисления в цели в эту цифру не вычитаются (более ранняя версия формулы это делала, из-за чего цифра не совпадала с ожидаемым «зарплата минус траты» — исправлено). При отрицательном значении карточка визуально подсвечивает предупреждение вместо простого красного числа.
- **Общий капитал** (`useNetWorth`): `Остаток ДС + накопительные счета + вклады + инвестиции` — намеренно **только** эти четыре ликвидные категории, без целей, без ипотеки и без остатка по кредитам (ипотека и кредиты — отдельная сущность с другой природой, см. ниже «Актив по ипотеке» и «Остаток долга»). Карточка показывает итог и разбивку по каждой из четырёх категорий.
- **Актив по ипотеке** (`useMortgageAssets`): отдельная карточка на Dashboard, по одной секции на каждую ипотеку, у которой заполнена «Текущая рыночная стоимость объекта» (без нее прирост посчитать нечем — такие ипотеки в карточке не показываются). Для каждой: текущая стоимость объекта, «Останется при продаже сегодня» (`currentValue − remaining`) и «Прирост с учётом расходов» — то же самое значение и та же формула, что и «Чистая прибыль от объекта» на карточке кредита (раздел 10), но также в процентах от суммы покупки (`calculateMortgageProfit`, `src/utils/calculations.ts` — общая функция для обоих мест, чтобы расчёт не разошёлся). Карточка «Остаток долга» по-прежнему показывает голый остаток долга по кредитам/ипотекам отдельно — «Общий капитал» его не включает.
- Блок «Сегодня»: доходы/расходы за сегодняшний день.
- **«На этой неделе»** (`useUpcomingPayments`, `src/hooks/useFinancials.ts`): единая хронологическая лента того, что реально спишется в ближайшие 7 дней — плановые платежи по кредитам/ипотекам (только пока остаток > 0), напоминания по долгам друзьям (у которых задана дата и они ещё не оплачены), страховые взносы (годовые — по дате окончания полиса, ежемесячные — по ближайшему числу месяца через `nextMonthlyOccurrence`) и активные регулярные платежи. Суммы по кредитам/ипотекам конвертируются в текущую валюту отображения. Показывается только если в ближайшую неделю что-то есть; при пустом списке карточка просто не рендерится.
- **«Календарь обязательств»**: тот же месячный календарь, что и в разделе «Кредиты и платежи» (раздел 10), вынесенный дополнительно на главный экран — по просьбе пользователя, чтобы не заходить в отдельный раздел ради общей картины. Источник данных общий — хук `useObligationEvents` (`src/hooks/useFinancials.ts`), поэтому обе точки показа синхронизированы и не могут разойтись. Показывается только если есть хотя бы одно отмеченное обязательство.
- **Остаток долга**: сумма остатков по всем кредитам и отдельно по всем ипотекам (`useDebtSummary`), с общим итогом, если заведены оба вида. Показывается только если есть хотя бы один кредит/ипотека.
- **Инвестиции** (`useInvestmentsSummary`): текущая стоимость портфеля (количество × текущая цена по всем активам) и, если были, сумма всех полученных дивидендов/купонов. Показывается только если стоимость портфеля больше 0.
- Последние 5 транзакций (`FlatList`).
- Прогресс-бары по лимитам категорий (бордовые), значение `spent` считается **динамически** из реальных транзакций за текущий календарный период — не хранится статично.
- Топ-3 категории расходов / топ-3 источника дохода.
- Финансовый прогноз на месяц вперёд (по среднему чистому потоку за все месяцы с операциями).

Файл: `src/screens/dashboard/DashboardScreen.tsx`, расчёты — `src/hooks/useFinancials.ts`.

## 7. Доходы и расходы

- **Остаток ДС по текущим счетам** — сводная строка над фильтрами, показывает текущий кассовый остаток (`useFreeFunds`, то же число, что и «Свободные средства» на Dashboard — доходы минус расходы по всем транзакциям). Подсвечивается красным при отрицательном значении.
- Один экран с переключателем Расходы/Доходы (`SegmentedControl`), список — `FlatList` с `useMemo`-фильтрацией.
- Фильтры: период (неделя/месяц/квартал/год/все), категория (чипы), поиск с debounce 300мс.
- Категории по умолчанию (расходы — 23, включая «Спорт», «Рабочие обеды», «Такси», «Красота и уход», «Питомцы», «Хобби», «Штрафы/пени», «Благотворительность», «Фотосессия»; доходы — 9) + возможность ввести свою (`src/theme/categoryIcons.ts`).
- Автокатегоризация по ключевым словам в комментарии (эвристика, офлайн, `src/utils/categorize.ts`).
- **Проверка на дубликат перед сохранением** (`isDuplicateTransaction`, `src/utils/validation.ts`) — совпадение суммы/категории/типа/комментария в пределах минуты. Раньше при совпадении сохранение жёстко блокировалось без возможности продолжить — из-за этого нельзя было внести две реально разные операции, которые просто случайно совпали по сумме и категории (например, два одинаковых по стоимости кофе за утро). Теперь это предупреждение с выбором: «Отмена» или «Всё равно добавить» — вторая кнопка сохраняет запись, несмотря на совпадение.
- **Редактирование и удаление**: тап по строке открывает форму редактирования (предзаполненную), свайп влево — удаление с подтверждением (`src/components/SwipeableTransactionRow.tsx`).
- Звук монетки (`expo-audio`) + вибрация (`expo-haptics`) при сохранении — управляются переключателями в Настройках.

Файлы: `src/screens/transactions/TransactionsScreen.tsx`, `AddTransactionScreen.tsx`.

## 9. Накопления

Один экран с переключателем: **Цели / Вклады / Счета / Инвестиции / Кэшбэк**.
- Цели: прогресс-бар, дедлайн, поддержка совместных целей с партнёром (два прогресс-бара). Под суммой «накоплено из целевой» — строка **«Осталось накопить: X»** (целевая сумма минус уже накопленное), чтобы не считать в уме; для совместной цели остаток берётся от суммы вкладов обоих участников — цель одна на двоих (например, путёвка), важен остаток до полной стоимости, а не до вклада одного человека. Когда остаток достигает нуля — вместо этого показывается «Цель достигнута!».
- Вклады: сумма, ставка, даты открытия/закрытия (фиксированный срок).
- **Накопительный счёт** (сегмент «Счета», `SavingsAccount`) — в отличие от вклада, без даты закрытия: текущий остаток и годовая ставка %, задаётся один раз при создании и правится вручную (пополнения/списания вносятся тем же полем «Текущий остаток» через редактирование). **Проценты начисляются автоматически на остаток в конце каждого календарного месяца** (`calculateMonthlyInterest` + `accrueSavingsInterest` в `src/store/financeStore.ts`): при каждом открытии приложения (`loadAll`) проверяется, сколько полных месяцев прошло с `lastAccrualDate` — если один или больше, проценты начисляются последовательно за каждый месяц (с учётом уже начисленных за предыдущий, то есть капитализацией), остаток увеличивается, а каждое начисление пишется в историю (`SavingsAccrual`, таблица `savings_accruals`). Карточка счёта показывает остаток, ставку, дату следующего начисления и сумму последнего начисления. Поскольку у приложения нет фонового процесса (Expo Go это не поддерживает), начисление «догоняющее» — срабатывает при следующем открытии приложения, а не строго в полночь конца месяца.
- **Перевод между накопительным счётом и текущим счётом — в обе стороны**, на карточке счёта (сегмент «Счета»): две кнопки, каждая раскрывает своё поле суммы с подсказкой доступного остатка.
  - **«Перевести на текущий счёт»** (`transferSavingsAccountToCash`, `src/store/financeStore.ts`) — уменьшает баланс счёта и добавляет транзакцию-доход с категорией «Перевод со счёта» на ту же сумму. Сумма не может превышать остаток счёта.
  - **«Пополнить с дохода»** (`depositToSavingsAccountFromCash`) — обратная операция: увеличивает баланс счёта и добавляет транзакцию-расход с категорией «Перевод на счёт» на ту же сумму, списывая её с текущего (кассового) остатка. Сумма не может превышать «Остаток ДС» (`useFreeFunds`) — с конвертацией в валюту счёта, если она отличается от текущей валюты отображения.
  - Раньше единственным способом отразить любой из этих переводов было вручную и отдельно менять «Текущий остаток» счёта и добавлять запись в «Доходы/Расходы» — легко было забыть один из двух шагов или разойтись в сумме. Обе кнопки делают это одним действием, и обе ограничены доступной суммой — поэтому ни баланс счёта, ни текущий (кассовый) остаток не могут уйти в минус.
- Инвестиции: тип актива (акции/облигации/крипта/ПИФ), количество, цена покупки/текущая, автоматический % доходности.
- **Автоматическое обновление цены с Мосбиржи** (`src/utils/moex.ts`, публичный ISS API — без ключа и регистрации): у актива есть необязательное поле «Тикер Мосбиржи» (`Investment.moexTicker`, например `SBER`), показывается для всех типов кроме крипты (крипта на Мосбирже не торгуется). Если тикер задан — «Текущая цена» подтягивается автоматически при каждом открытии вкладки «Инвестиции» (`fetchMoexPrice`, тихо игнорирует ошибки при автообновлении — нет интернета/тикер временно недоступен просто оставляет прежнюю цену) и по кнопке «Обновить цену с Мосбиржи» на карточке актива (при нажатии ошибки показываются явно через `Alert`). Акции и ПИФ запрашиваются через рынок `shares`, облигации — через рынок `bonds`, конкретный борд (TQBR/TQTF/TQOB и т.п.) не указывается — ISS сам возвращает все борды, где торгуется тикер; берётся первая строка с ценой последней сделки (`LAST`), а если торги ещё не шли — цена закрытия предыдущей сессии (`PREVPRICE`). Количество и цена покупки по-прежнему вводятся вручную — автоматизируется только текущая рыночная цена.
- **Поиск тикера по названию** (`searchMoexSecurities`, `src/utils/moex.ts`): тикер — это короткий биржевой код (SBER, X5 и т.п.), а не название компании, и пользователи не знают его наизусть — ввод "Сбербанк" или "Х5" в поле тикера не находил цену. Кнопка «Найти тикер по названию» в форме актива ищет через публичный поисковый эндпоинт ISS (`/iss/securities.json?q=...`) по тому, что введено в поле тикера, либо по названию актива, если поле тикера пустое; результаты (только реально торгуемые бумаги, `is_traded=1`, без дублей по `secid`) показываются списком — тап по строке подставляет правильный тикер в поле.
- **Дивиденды и купоны по инвестициям** (`InvestmentPayout`): на карточке актива — кнопка-раскрытие с меткой «Дивиденды» (для акций) или «Купоны» (для облигаций и остальных типов — «Выплата»), тип метки определяется по `assetType`, отдельно не хранится. В развёрнутом виде — история выплат (сумма + дата, с редактированием/удалением через `CardActions`, как и в истории погашений кредита) и форма добавления новой выплаты. Сумма всех выплат по активу показывается прямо на карточке. Выплаты не меняют количество/цену актива — это отдельный учёт полученного дохода, а не переоценка портфеля.
- Кэшбэк-карты: % кэшбэка, накопленная сумма.
- Каждая карточка — иконки ✏️/🗑 (редактировать/удалить, `src/components/CardActions.tsx`) с подтверждением перед удалением.

Модель начислений по счетам — `src/store/financeStore.ts` (`saveSavingsAccount`, `accrueSavingsInterest`), `src/database/repository.ts` (`savings_accounts`, `savings_accruals`). ## 10. Кредиты и платежи

Один экран с переключателем: **Кредиты / Ипотека / Календарь / Долги / Страховка**.
- Кредиты и ипотека используют одну модель данных (`Credit`) с полем-дискриминатором `kind: 'credit' | 'mortgage'` и **общий код рендера** (`renderCreditCard`, `renderCreditForm`) — экран лишь фильтрует список по `kind`. Поэтому все пункты ниже (ручной остаток, ручной ежемесячный платёж, «Внести платёж», график, календарь и т.д.) действуют в разделе «Ипотека» ровно так же, как и в «Кредиты» — это не два отдельных набора логики, а один и тот же. У ипотеки дополнительно есть необязательные поля: объект недвижимости (`propertyAddress`) и первоначальный взнос (`downPayment`).
- **Дата выдачи** (`startDate`) — обязательное поле формы (раньше проставлялась автоматически и не была видна пользователю).
- **Текущий остаток долга (на сегодня)** — необязательное поле формы для случая, когда вносится уже действующий кредит/ипотека без просрочек: если оставить пустым, остаток по умолчанию равен полной сумме (как для нового кредита); если указать вручную реальный остаток на сегодняшний день, все дальнейшие платежи (плановые и досрочные) будут считаться именно от этой суммы, а не от исходной суммы кредита. При редактировании существующего кредита это же поле предзаполняется текущим остатком и позволяет скорректировать его в любой момент.
- **Ежемесячный платёж** — тоже необязательное поле формы: по умолчанию считается по аннуитетной формуле (`calculateMonthlyPayment`), но эта формула исходит из полной суммы и полного срока и не всегда совпадает с реальным платёжным поручением банка (особенно для кредита, заведённого не с нуля, или если банк считает платёж иначе). Поле позволяет задать точную сумму платежа вручную — именно она используется и в «Внести платёж», и в графике погашения, и при делении на проценты/основной долг.
- В начале списка каждого сегмента — сводная карточка с общим остатком долга (по кредитам / по ипотеке отдельно).
- Прогресс погашения, график платежей: до 12 ближайших платежей, рассчитанных **от текущего фактического остатка** (`c.remaining`) через `calculateAmortizationStep`, а не от исходной суммы кредита по формуле «как будто ни один платёж ещё не сделан» — раньше график не менялся после внесения платежей и не соответствовал реальному состоянию кредита. Каждая строка графика показывает реальную дату платежа, отсчитанную от `c.nextPaymentDate` (+1 месяц на каждый следующий платёж) — не от даты выдачи кредита (`startDate`), так как день списания по кредиту часто отличается от дня выдачи.
- **Дата следующего платежа** (`nextPaymentDate`) — теперь редактируемое поле формы (по умолчанию — через 30 дней от создания), а не проставляется автоматически и незаметно. Именно это поле управляет отметками в календаре, поэтому календарь и карточка кредита всегда показывают одну и ту же дату.
- **Обычный (плановый) платёж, «Внести платёж»**: в развёрнутой карточке — отдельная форма (сумма + дата), которая через `makePayment` корректно разбивает платёж на проценты и основной долг (`calculateAmortizationStep` в `src/utils/calculations.ts`: сначала списываются проценты на текущий остаток по ставке кредита, оставшаяся часть уменьшает сам долг) и **автоматически сдвигает `nextPaymentDate` на месяц вперёд**. Раньше остаток по кредиту двигали только досрочные погашения — обычные платежи вообще не отражались на балансе, из-за чего расчёты расходились с реальностью.
- **Досрочное погашение с датой** (отдельная форма, ниже «Внести платёж»): запрашивает сумму и дату, вся сумма целиком уходит в счёт основного долга. Каждое погашение (плановое или досрочное) пишется в общую историю (`CreditRepayment`, таблица `credit_repayments`) с типом «регулярный», «частичное» или «полное» (полное — когда остаток доходит до 0). История видна в развёрнутой карточке кредита/ипотеки; при полном погашении карточка также показывает дату полного погашения отдельной строкой.
- **Редактирование и удаление записей истории погашений** — иконки (`CardActions`) на каждой строке истории. Каждая запись хранит `principalPortion` — сколько из её суммы реально ушло в счёт основного долга (для «регулярных» платежей это часть за вычетом процентов, для досрочных — вся сумма). Остаток по кредиту всегда равен «остаток до = остаток после + principalPortion этой записи», поэтому:
  - **Удаление** записи (`removeCreditRepayment`) просто возвращает её `principalPortion` обратно в `remaining`.
  - **Редактирование** (`editCreditRepayment`) сначала откатывает старое влияние записи на `remaining`, затем пересчитывает новую сумму (через `calculateAmortizationStep`, если тип «регулярный», иначе — вся сумма в основной долг) и заново уменьшает `remaining`.
  - Это делает `remaining` корректным независимо от того, какая по счёту запись редактируется/удаляется, без необходимости пересчитывать всю историю целиком. Дата следующего платежа (`nextPaymentDate`) при этом не трогается — если удаляется/меняется последний регулярный платёж, дату следующего платежа при необходимости нужно поправить вручную в форме кредита.
- **Процентная ставка не округляется**: поле «Ставка %» и все денежные/процентные поля используют `parseLocaleNumber` (`src/utils/parseNumber.ts`), который понимает и точку, и запятую как десятичный разделитель, и клавиатуру `decimal-pad` (в отличие от `numeric`, у которой на многих телефонах просто нет клавиши разделителя). Раньше `parseFloat` обрезал ввод по запятой (`parseFloat("19,9")` → `19`), из-за чего «19,9%» превращалось в «19%» — теперь ставка и суммы сохраняются и отображаются с полной точностью.
- Календарь: свой компонент месячной сетки (`MiniCalendar`) с отметками дат платежей по кредитам/регулярным платежам/долгам/страховкам. **По нажатию на дату** под календарём появляется сноска со списком платежей на эту дату (название кредита/ипотеки/долга/страховки/регулярного платежа и сумма) — или «На эту дату платежей не запланировано», если дата пустая. Список событий строится общим хуком `useObligationEvents` (`src/hooks/useFinancials.ts`) — тот же источник данных использует одноимённая карточка на главном экране (раздел 6), чтобы не разошлись два места с одной и той же логикой.
- Локальные напоминания (`expo-notifications`) за 3 и 1 день до платежа (для долгов друзьям) и повторяющиеся ежемесячные/ежегодные для страховки и регулярных платежей — см. ниже.
- **Регулярные платежи с окном оплаты**: у `RegularPayment` есть необязательное поле `dayOfMonthEnd` — если задано, платёж можно вносить в любой день от `dayOfMonth` до `dayOfMonthEnd` включительно (например, ЖКХ — с 1 по 10 число), а не строго в одну дату (как интернет). В календаре отмечается каждый день окна, а не только первый — видно все дни, когда платёж ещё можно внести. Напоминание (`scheduleRegularPaymentReminder`, `src/utils/notifications.ts`) — повторяющееся ежемесячное на день начала окна (`dayOfMonth`), с текстом, указывающим весь диапазон, если он задан.
- **Число месяца всегда обрезается по реальному количеству дней в конкретном месяце** (`daysInMonth` в `useObligationEvents`, `src/hooks/useFinancials.ts`) — без этого «31 число» в феврале (28 дней) молча перетекало бы на 1-3 марта через нативный `Date` и помечало бы чужой месяц под чужой подписью. Также ежемесячные события (регулярные платежи, ежемесячная страховка) генерируются не только на текущий календарный месяц, а на скользящее окно из 4 месяцев (−1…+2 от сегодняшнего) — иначе при пролистывании `MiniCalendar` вперёд/назад такие события пропадали бы совсем, будто их не будет в другие месяцы.
- **Платежи по кредитам/ипотекам в календаре тоже повторяющиеся**, а не разовая отметка на `nextPaymentDate` — по дню месяца `nextPaymentDate` отмечаются ещё 2 месяца вперёд (`CREDIT_MONTH_WINDOW`), чтобы платёж был виден как регулярный. Назад не заглядывает (в отличие от регулярных платежей/страховки) — `nextPaymentDate` это уже ближайший неоплаченный платёж, месяцы до него по этому кредиту уже погашены и видны в истории погашений кредита, а не в календаре будущих обязательств. Полностью погашенные кредиты (`remaining <= 0`) в календаре не показываются вовсе — платить по ним больше нечего.
- **Раздел «Регулярные платежи»** (боковое меню, `src/screens/regularPayments/RegularPaymentsScreen.tsx`) — полноценный CRUD для обязательных ежемесячных платежей, не привязанных к кредиту/подписке: ЖКХ, интернет и ТВ, детский сад, курсы, кружки и т.п. (раньше `RegularPayment` вообще не имел формы создания — существовал только как демо-данные и через импорт JSON). Форма: название, сумма, категория (свободный текст), тип (расход/доход), переключатель «Диапазон дат оплаты» (при включении — два поля «с числа»/«по число» вместо одного «День оплаты»), «Активен». Напоминание планируется только при создании (как и у страховки/долгов) — редактирование существующего платежа не плодит повторных уведомлений.
- **Периодичность взноса по страховке** (`InsurancePolicy.paymentFrequency: 'monthly' | 'annual'`, выбор `SegmentedControl` в форме полиса, **по умолчанию — «Ежегодно»**) — определяет и напоминание, и отметки в календаре:
  - **Ежегодно** (обычная схема — ОСАГО/КАСКО, а также большинство ипотечного страхования жизни/объекта): напоминание — повторяющееся, через `YearlyTriggerInput`, на дату «`endDate` минус 30 дней», каждый год — в отличие от прежней версии, которая планировала уведомление только один раз при создании полиса и переставала напоминать со второго года. В календаре отмечается сама дата окончания (`endDate`).
  - **Ежемесячно** (реже — для полисов с помесячным взносом): напоминание — по-настоящему повторяющееся, через `MonthlyTriggerInput` (день месяца из `endDate.getDate()`, каждый месяц), а не разовое. В календаре отмечается ближайшая в текущем месяце дата взноса.
  - Планирование — `scheduleInsuranceReminder` (`src/utils/notifications.ts`).
- Долги друзьям (я должен / мне должны), страховые полисы.
- Редактирование и удаление для кредитов, ипотек, долгов и страховок — иконки на карточке (`CardActions`).
- **Чистая прибыль от объекта ипотеки** — только для `kind === 'mortgage'`, только если заполнено поле «Текущая рыночная стоимость объекта» (`currentValue`, необязательное поле формы). Карточка ипотеки дополнительно показывает:
  - **Выплачено процентов на сегодня** — не сумма вручную внесённых в приложение платежей (для кредита, взятого много лет назад, пришлось бы вносить каждый прошедший месяц вручную), а **симуляция амортизации** от даты выдачи (`startDate`) до сегодня по сумме платежа (`monthlyPayment`) и ставке (`rate`), с наложением всех зафиксированных досрочных погашений («частичное»/«полное» в истории) в их реальные даты — `simulateAmortization` (`src/utils/calculations.ts`), используется и на карточке кредита, и в `useMortgageAssets`. Обычные плановые платежи (тип «регулярный») в эту симуляцию не подставляются — они не нужны: платить их вручную за каждый месяц не требуется, только выдача, ставка и досрочные погашения, если были.
  - **Расходы на ремонт** — необязательное поле формы `renovationCosts` (общая сумма, задаётся/правится вручную, без отдельной истории по датам).
  - **Страховые взносы** — сумма всех полисов страхования (раздел «Страховка»), привязанных к этой ипотеке. Полис можно привязать к конкретной ипотеке через `SegmentedControl` в форме полиса (показывается только если есть хотя бы одна ипотека) — хранится как `InsurancePolicy.creditId`. **`InsurancePolicy.amount` (поле формы «Сумма взноса») — это стоимость ОДНОГО платежа за период** (`paymentFrequency`), а не совокупная сумма страхования за все годы владения. Расчёт просто складывает `amount` всех привязанных к ипотеке записей — поэтому для многолетней ипотеки со страховкой, продлеваемой ежегодно, нужно добавлять отдельную запись полиса на каждый оплаченный год (а не редактировать одну и ту же запись «поверх»), иначе сумма отразит только последний взнос, а не реальные суммарные расходы на страхование. Форма подсказывает это прямым текстом при наличии хотя бы одной ипотеки.
  - **Чистая прибыль от объекта на сегодня** = `currentValue − (amount + downPayment) − выплаченные_проценты − renovationCosts − страховка`. Формула не учитывает погашение тела долга отдельной строкой: оно уже отражено в равенстве (наличные превращаются в собственный капитал 1 к 1), поэтому вычитаются только реальные затраты на владение — проценты, ремонт, страховка.
  - **Останется при продаже сегодня** = `currentValue − remaining` — отдельная от «чистой прибыли» величина: сколько денег реально окажется на руках, если продать объект сегодня. Здесь остаток основного долга (`remaining`) вычитается напрямую, потому что при продаже банку нужно вернуть именно эту сумму — это вопрос наличных после сделки, а не вопрос доходности вложения.

### Реальная интеграция с ИИ (Claude)

- **Как устроено**: у приложения нет собственного backend — это чистый мобильный клиент с локальной SQLite-базой. Поэтому обращение к Anthropic API идёт **напрямую с телефона** (`fetch` на `https://api.anthropic.com/v1/messages`, модель `claude-haiku-4-5-20251001`) — `src/utils/claudeApi.ts` (`askClaude`). Это осознанный компромисс, подходящий для личного использования одним человеком; для публикации в App Store/Google Play ключ пришлось бы прятать за собственным backend-прокси, чтобы не раскрывать его на устройстве.
- **API-ключ** вводится пользователем в Настройках и хранится **только** в `expo-secure-store` (как и PIN/пароль) — `src/store/aiStore.ts`. В состоянии стора держится лишь факт наличия ключа (`hasApiKey`), сам ключ читается из secure-store непосредственно перед запросом и никогда не задерживается в React-состоянии дольше необходимого. «Сбросить все данные» тоже удаляет ключ.
- **Что отправляется**: не сырые транзакции, а компактная агрегированная сводка — доходы/расходы, норма сбережений, топ категорий расходов, лимиты бюджета (`buildFinancialSummaryPrompt`, `src/utils/aiInsights.ts`, покрыта тестами). Модель отвечает 3–4 конкретными рекомендациями на русском обычным текстом (без markdown), которые показываются как есть.
- **Экран** (`src/screens/extra/AiInsightsScreen.tsx`): если ключ не задан — подсказка и кнопка «Перейти в настройки». Если задан — **анализ обновляется автоматически**, без нажатия кнопки: экран строит промпт из текущих данных и сравнивает его с `aiStore.lastPrompt` (кэш последнего запроса, персистится в AsyncStorage); если ничего не изменилось — просто показывает кэш `lastInsight` мгновенно, без обращения к API; если данные изменились (внесена новая транзакция, лимит, категория расходов и т.п.) — запрос уходит сам в фоне. Кнопка «Обновить сейчас» остаётся для принудительного повторного запроса (например, после ошибки). Встроенная эвристика (`generateInsights`) остаётся ниже как офлайн-запасной вариант, который работает всегда, даже без ключа и без интернета.

## 16. Настройки

- Валюта: RUB/USD/EUR с курсом к рублю. **Курс можно подставить автоматически** — кнопка «Подставить курс ЦБ РФ» (`src/utils/cbr.ts`, `fetchCbrRate`) тянет официальный ежедневный курс с `cbr.ru` (публичный XML-эндпоинт `XML_daily.asp`, без ключа) и записывает его в поле курса; поле остаётся редактируемым, потому что банки применяют свою наценку/спред — официальный курс ЦБ это ориентир для автозаполнения, а не финальное значение, которое приложение навязывает. Автоподстановка ничего не делает сама по себе — только по нажатию кнопки, чтобы не затирать вручную подобранный пользователем курс при каждом открытии Настроек. XML парсится не полноценным парсером, а точечным регэкспом по нужной валюте (`extractCbrRate`) — устойчив к тому, что ответ ЦБ в кодировке windows-1251 (кириллица бьётся, но нужные ASCII-цифры и код валюты — нет). **Курс реально используется** — суммы конвертируются (`src/utils/currency.ts`), а не просто меняется значок валюты. Это касается не только транзакций, но и **кредитов/ипотек, вкладов, инвестиций и накопительных счетов** — у каждой такой записи есть собственное поле `currency` (валюта фиксируется в форме при создании, по умолчанию — текущая валюта отображения, и сохраняется при редактировании неизменной). При смене валюты в Настройках все суммы этих сущностей — на карточках, в сводных итогах (`useDebtSummary`, `useInvestmentsSummary`, `useNetWorth`, `useMortgageAssets`), в графике погашения — конвертируются в текущую валюту отображения через `convertAmount`, а не отображаются «как есть» под новым значком. Расчёты (амортизация, симуляция процентов) всегда идут в собственной валюте записи — конвертация происходит только в момент форматирования для показа.
- Тёмная/светлая тема, выбор цветовой схемы.
- Смена метода входа (PIN/пароль/биометрия).
- **API-ключ ИИ** (Claude/Anthropic) — ввод/удаление, статус «Ключ сохранён», кнопка перехода на страницу получения ключа. См. раздел 15 выше.
- Экспорт CSV (`;`, UTF-8), JSON, PDF. **CSV и PDF экспортируют транзакции за выбранный период** — переключатель «Всё время / Этот месяц / Прошлый месяц / Этот год» над кнопками экспорта (`filterTransactionsByPeriod`, `src/utils/period.ts`); заголовок PDF-отчёта отражает выбранный период. **Экспорт JSON — всегда полный бэкап**, период на него не влияет: не только транзакции/цели/кредиты/лимиты, а все сущности приложения (кредиты и их погашения, регулярные платежи, вклады, накопительные счета и их начисления, инвестиции и выплаты по ним, долги друзей, страховки, вишлист, уведомления, кэшбэк-карты, достижения, шаблоны трат, профиль) — см. `BackupData` в `src/utils/backup.ts`.
- **Импорт из JSON-файла — реально восстанавливает данные в БД**, а не просто читает файл. `reviveBackupData()` (`src/utils/backup.ts`) превращает распарсенный JSON обратно в типизированные записи (восстанавливает `Date`-поля из ISO-строк, подставляет `currency: 'RUB'` для записей из старых экспортов без этого поля). Затем `financeStore.importBackup()` записывает каждую сущность в SQLite через соответствующие `upsert*`-функции репозитория (для сущностей без upsert-обёртки — `transactions`, `creditRepayments`, `investmentPayouts`, `savingsAccruals`, `notifications` — сначала пробует `insert`, а если запись с таким id уже есть, откатывается на `update` (для транзакций/погашений/выплат) либо, там где update-функции нет (начисления, уведомления), просто пропускает как уже импортированную) и перезагружает состояние стора. Импорт можно безопасно повторять — записи с существующим id обновляются, а не дублируются. После импорта показывается количество реально распознанных записей (`countBackupEntries`).
- **Импорт выписки банка (CSV)** (`src/screens/transactions/BankImportScreen.tsx`, кнопка в Настройках → «Экспорт и импорт», открывается через глобальный `navigateGlobal('BankImport')` — сам экран зарегистрирован третьим в стеке «Транзакции», рядом с «Новая транзакция», см. `TabsNavigator.tsx`) — превращает CSV-выписку из банковского приложения в транзакции, без ручного ввода каждой операции. Формат у банков не стандартизован, поэтому вместо парсера под конкретный банк — три шага: 1) выбор файла (свой лёгкий парсер `src/utils/csv.ts`, без сторонних библиотек — понимает и запятую, и точку с запятой, кавычки с экранированием, оба порядка даты ГГГГ-ММ-ДД/ДД.ММ.ГГГГ, и суммы в любом привычном виде — с пробелами/точкой/запятой как разделителем тысяч, в скобках для отрицательных, со значком валюты); 2) сопоставление столбцов (какой — дата, какой — сумма, какой — описание, и как понимать знак суммы — «минус = расход» или наоборот, банки делают по-разному) — один раз за импорт; 3) предпросмотр распознанных операций (с подсчётом пропущенных нераспознанных строк) перед подтверждением. **Категория подбирается автоматически** через ту же эвристику по ключевым словам (`suggestCategory`, `src/utils/categorize.ts`), что уже использовалась для поля «Комментарий» при ручном вводе — не найдено совпадение — попадает в категорию «Другое». Валюта операций — текущая валюта отображения (как и при ручном добавлении транзакции).
- Сброс всех данных (полностью очищает БД, secure-store — включая PIN/пароль и API-ключ ИИ — и статус онбординга).
- Версия приложения.

Файл: `src/screens/settings/SettingsScreen.tsx`.

## 17. Обработка ошибок и качество кода

- `ErrorBoundary` оборачивает каждый экран (`src/components/withErrorBoundary.tsx`) — при падении показывает «Что-то пошло не так» + кнопку «Обновить».
- **Клавиатура не перекрывает нижние поля форм**: `ScreenContainer` (`src/components/ScreenContainer.tsx`) оборачивает контент в `KeyboardAvoidingView` (`behavior="padding"` на iOS, `"height"` на Android) — раньше на длинных формах (например, добавление кредита или инвестиции) всплывающая клавиатура закрывала нижние поля ввода и кнопку «Сохранить» без возможности прокрутить к ним. Так как это общий компонент, использующийся почти на каждом экране, фикс применяется сразу везде, а не по одному экрану.
- Списки транзакций — `FlatList` с `useMemo`/`useCallback` (не `ScrollView.map`).
- Уникальные ID — `uuid v4` (`react-native-uuid`).
- Тесты: **184 теста** (Jest + React Native Testing Library) — покрывают все утилиты (`src/utils/`, включая парсер CSV-выписок `csv.test.ts`), несколько ключевых компонентов (`AppButton`, `ProgressBar`), бизнес-логику стораджа (`financeStore.test.ts`, `aiStore.test.ts` — репозиторий БД и `expo-secure-store` замоканы) и хуки `useUpcomingPayments`/`useObligationEvents` (через `renderHook` из `@testing-library/react-native`).
- Комментарии в коде — на русском, только там, где логика неочевидна (не построчно).
- **CRUD везде одинаковый**: у каждой сущности с собственным экраном (транзакции, цели, вклады, инвестиции, кэшбэк, кредиты, долги, страховки, лимиты бюджета, вишлист, шаблоны) есть удаление (`confirmDelete` + подтверждение) и редактирование (тап/иконка открывает ту же форму добавления, предзаполненную текущими значениями). Хранилище (`financeStore`) поддерживает upsert по `id` для всех сущностей, кроме транзакций — для них отдельно есть `editTransaction`.

### Правки по итогам сплошной проверки приложения на корректность
- **«Зависшая» форма при сбое напоминания**: сохранение записи (регулярный платёж, кредит/ипотека, долг, страховка, обычная транзакция) и последующая постановка уведомления/вибрации раньше шли одной цепочкой — если планирование уведомления падало с ошибкой уже после успешного сохранения, форма не закрывалась, хотя запись была сохранена. Теперь такие вызовы обёрнуты в `try/catch` (`RegularPaymentsScreen`, `CreditsScreen` — добавление кредита/долга/страховки, `AddTransactionScreen` — вибрация, `BudgetScreen` — вибрация при уведомлении о лимите). Отдельная проблема — `try/catch` не спасает, если промис не падает с ошибкой, а **зависает без ответа** (наблюдалось при запросе разрешения на уведомления в Expo Go на Android): все вызовы `expo-notifications` в `src/utils/notifications.ts` теперь дополнительно ограничены таймаутом 5 секунд (`withTimeout`) — если ответа нет, планирование напоминания просто не происходит, а сохранение формы не блокируется.
- **Пустая обязательная форма молчала**: нажатие «Сохранить» с незаполненным обязательным полем (название/сумма) в «Регулярных платежах» и в «Кредитах» (добавление кредита, долга, страховки) раньше просто ничего не делало, без подсказки — на вид неотличимо от неработающей кнопки. Теперь показывается `Alert` с указанием, что именно заполнить.
- **Поля формы «наследовали» значения предыдущей записи**: `resetForm()` в «Сбережениях» (даты открытия/закрытия вклада, срок цели, тип актива) и в «Кредитах» (дата напоминания по долгу, дата окончания страховки, статус долга) сбрасывал не все поля формы — при открытии формы для второй записи подряд часть полей молча оставалась от предыдущей. Дополнено полным сбросом.
- **Иконки редактирования/удаления обрезались**: заголовок карточки (например, длинное название ипотеки) не уступал место иконкам справа и мог вытеснить их за край экрана. Исправлено единым образом во всех списках с такой же структурой — заголовок при необходимости переносится на вторую строку, иконки всегда полностью видны (`CreditsScreen`, `RegularPaymentsScreen`, `SavingsScreen`, `BudgetScreen`, `WishlistScreen`, `RecurringTemplatesScreen`). Тот же принцип применён к сводным строкам на Dashboard («Остаток долга», «Актив по ипотеке») — длинная подпись плюс длинное значение (сумма + процент) больше не наезжают друг на друга.
- **Перенос текста вкладки посреди слова**: `SegmentedControl` при 4+ вкладках (например, «Кредиты / Ипотека / Календарь / Долги / Страховка») делил ширину поровну, из-за чего слово вроде «Календарь» переносилось на новую строку. Шрифт при этом не уменьшался — вместо этого при 4+ вкладках лента стала горизонтально прокручиваемой, каждая вкладка занимает столько места, сколько нужно её тексту (`src/components/SegmentedControl.tsx`). Переключатели с 2-3 вариантами (Расход/Доход и т.п.) визуально не изменились.
- **«The action NAVIGATE... was not handled by any navigator» при добавлении дохода/расхода из бокового меню**: экраны «Доходы»/«Расходы» — отдельные стеки бокового меню (см. раздел 3), а форма добавления транзакции (`AddTransaction`) была зарегистрирована только внутри стека вкладки «Транзакции». React Navigation ищет целевой экран в текущем стеке и по цепочке родителей, но не у «соседних» стеков бокового меню — поэтому кнопка «+» и тап по записи в «Доходы»/«Расходы» падали с этой ошибкой, хотя в «Транзакциях» всё работало. Тот же класс ошибки был и у кнопки «Импорт выписки банка» в Настройках (`BankImport` зарегистрирован только в стеке «Транзакций», а вызывается из стека «Настройки»), и у перехода по уведомлению о превышении лимита бюджета (ссылалось на вкладку «Budget», которая вложена в «Tabs», а переход шёл из отдельного стека «Уведомления» — эта ошибка была не видна пользователю, так как была молча проглочена `try/catch`, но переход просто не срабатывал). Исправлено: `createSimpleStack` (`src/navigation/SimpleStack.tsx`) научился принимать `extraScreens` — дополнительные экраны в том же стеке; `AddTransaction` добавлен в стеки «Доходы»/«Расходы», `BankImport` — в стек «Настройки». Переход по уведомлению о лимите теперь идёт через `navigateGlobal('Tabs', { screen: 'Budget' })` — с явным указанием вложенной вкладки, а не голым именем.

## 19. Как запустить

См. `README`-инструкцию в переписке или:
```
npm install
npx expo start --tunnel
```
Отсканировать QR в приложении Expo Go. **Важно**: Expo Go на устройстве должен поддерживать SDK 54 (проверяется в приложении: Profile → SDK version).

### Постоянная ссылка/установочный файл без запущенного компьютера (EAS Build)

`npx expo start --tunnel` требует, чтобы компьютер с проектом был включён и подключён к интернету в момент запуска приложения — неудобно для постоянного использования. Решение — сборка реального `.apk`-файла через **EAS Build**: после сборки приложение устанавливается на телефон и работает независимо от Expo Go, тоннеля и компьютера.

**Конфигурация** — `eas.json` (профиль `preview`: внутренняя раздача, тип сборки `apk`) и `android.package: "com.familyfinance.app"` в `app.json`.

**Важно — про инцидент с потерей данных.** Первая попытка подключить EAS Build привела к полному сбросу хранилища приложения в Expo Go (все данные пропали, приложение заново запросило настройку входа). Причина — по времени совпадает с тем, что `eas build` при первой линковке проекта дописывает в `app.json` поле `extra.eas.projectId`; похоже, что Expo Go использует это поле как часть ключа, по которому изолирует хранилище одного проекта от другого — то есть **самая первая линковка к EAS, скорее всего, неизбежно один раз "переключает" хранилище на новое**, независимо от того, насколько аккуратно это сделано. Поэтому это не разовая случайность, которую можно просто обойти, а ожидаемое разовое событие, к которому нужно быть готовой.

**Порядок действий (обязательно в этом порядке):**
1. **Сначала сделать свежий бэкап** — Настройки → «Экспорт и импорт» → экспорт в JSON, сохранить файл в надёжном месте (не только на телефоне — например, отправить себе на почту или в облако). Без этого шага не продолжать.
2. `git pull origin claude/application-pt781p`, затем `npm install` (подтянет `eas-cli`, если его ещё нет).
3. `npx eas login` — войти под аккаунтом `ksenia_13`.
4. `npx eas build --platform android --profile preview` — первая сборка. Если Expo Go в этот момент потеряет данные приложения на телефоне (см. выше) — это ожидаемо, не повод останавливаться.
5. Дождаться ссылки на сборку (обычно 10–20 минут, EAS присылает и на почту), скачать и установить `.apk` на телефон (потребуется разрешить установку из неизвестных источников).
6. Открыть собранное приложение → Настройки → «Экспорт и импорт» → импорт из того же JSON-файла, что сохранили в шаге 1 — данные вернутся.
7. Дальше это уже отдельное, самостоятельно работающее приложение — обновлять его нужно новой сборкой EAS (или `eas update`, если понадобится), а не через `expo start --tunnel`.
